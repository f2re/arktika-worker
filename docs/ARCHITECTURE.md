# Архитектура MVP и границы масштабирования

## Текущая схема

```text
Браузер: календарь / карта / легенда / точка / маршрут
             │ localhost, cookie, JSON
Python HTTP API — Workstation — реестр продуктов
     │           │             │
     │           │             ├─ Rasterio / PROJ / NumPy / Pillow
     │           │             ├─ временная папка → атомарный продукт
     │           │             └─ маршрут на исходных пикселях
     │           └─ SQLite: каталог / сцены / полнота / настройки
     └─ клиент GPTL → STAC / OAuth / STS → S3
                         └─ очередь Range/ETag → архив GeoTIFF
```

Модульный монолит выбран сознательно: один процесс, одна база, нет обязательных Redis/Celery/PostGIS/Node-сервисов. Набор внешних зависимостей ограничен георастровым стеком. Подложка и код интерфейса локальные, внешний tile provider не нужен.

Сетевой слой отделён от научного: GDAL читает локальные файлы, не произвольные URL. Метаданные каталога нормализуются до обработки. Выдача STS не трактуется как разрешение прочитать все объекты. Загрузчик использует один механизм авторизации для пробного чтения и фактической передачи данных.

Один фоновый слот для поиска, импорта и обработки; один сохраняемый загрузчик. HTTP обслуживает небольшое ограниченное число запросов. SQLite WAL и lock защищают внутренние записи. Нативная обработка использует один поток GDAL для предсказуемого потребления памяти. Тяжёлое параллельное производство — не задача текущего HTTP ThreadingServer.

## Контракты модулей

`network` отвечает только за транспорт и пагинацию. `model` — за понятия/идентификаторы/время. `store` — за индекс и состояния. `processing` — за чистую физическую арифметику после калибровочного барьера и экспорт. `geo` — за единый transform карты, Солнце и геодезию. `routes` не получает право объявлять прогноз. `motion` не получает право объявлять ПМЦ. `profiles` требует внешние профили.

`products.registry()` является источником состава интерфейса, описаний, единиц и статусов. Производственный алгоритм должен возвращать продукт с легендой и происхождением, а не только PNG.

## Что масштабируется без замены архитектуры

Добавление рецептов, версий калибровки, областей, валидаторов, адаптеров наблюдений, асинхронного COG-тайлинга и фонового индексатора. Локальная эксплуатация может оставаться монолитной. Перед оптимизацией измерять чтение каталога, дисковый ввод, память warp и стоимость отрисовки; не строить распределённую очередь по предположениям.

## Когда нужны отдельные сервисы

Несколько одновременных операторов, централизованный архив, одновременные задания на разные регионы, защищённая публикация, постоянное поступление снимков. Тогда HTTP переносится на поддерживаемый production ASGI/WSGI-сервер, вводятся пользователи/роли/CSRF/TLS/audit, хранение объектов отделяется от каталога, SQLite заменяется при необходимости на PostgreSQL/PostGIS, вычисления уходят в ограниченную очередь процессов.

Ни один из этих компонентов не обязателен для локального MVP. S3-совместимое хранилище может располагаться на существующем NAS; включение его в будущем не означает зависимость от внешнего облака.

## Отказы и восстановление

HTTP 500 каталога: статус ошибки, данные других платформ не объявляются отсутствующими. Разрыв сети: сохранение корректной части и проверка версии объекта при продолжении. Изменившийся исходник: новый продукт, не подмена происхождения старого. Отмена обработки: `.building` не показывается как готовая продукция. Недостаток места: загрузка останавливается до переполнения; для производства больших растрoв требуются дополнительные квоты.

Токены исчезают при перезапуске процесса. Очередь сохраняется и переводится в паузу. Автоматическое удаление архива не реализовано; резервное копирование и дисковые квоты задаются эксплуатацией.
