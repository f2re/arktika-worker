# Разработка

Перед изменениями изучить README, docs/ARCHITECTURE.md, docs/SCIENCE.md и AGENTS.md. Работать в отдельной ветке, не переписывать историю main. В PR указать задачу, изменение контракта данных, выполненные тесты и влияние на неопределённость продукта.

Подготовка: `python install.py`. Проверка: `.venv/bin/python -m unittest discover -s tests -v`; дополнительно `node --check static/app.js` при наличии Node. Работа приложения от Node не зависит.

Тесты на искусственных массивах проверяют арифметику и интерфейсы, а не качество метеопродуктов. Реальные данные для приёмки должны иметь проверяемое происхождение и не включаться в Git без подтверждения прав распространения. В тестовой fixture явно писать `SYNTHETIC UNIT TEST ONLY`.

Новые продукты добавлять в products.py с единицами, входами, рецептом, интерпретацией экстремумов, легендой, маской и статусом верификации. Изменения алгоритма требуют смены версии рецепта и кэша. Любое новое значение должно сохранять различие между отсутствием данных, нулём, неопределённостью и отрицательным результатом.

Предпочтительны небольшие модули, явные единицы и типы, независимые чистые функции для научной части. В текущем MVP часть кода компактна; план рефакторинга предполагает полные аннотации типов и отделение HTTP-маршрутов до расширения серверной версии. Не добавлять распределённые сервисы до появления измеренной необходимости.
